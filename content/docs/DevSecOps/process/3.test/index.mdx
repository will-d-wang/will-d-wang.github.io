# Testing Strategy

Testing allocates confidence across layers. The goal is not maximum test count; it is fast, trustworthy evidence about the failures that matter to users and operators.

| Layer | Best for | Common limitation |
| --- | --- | --- |
| Static analysis | Known code patterns, types, policy, and secrets | Cannot establish runtime behavior |
| Unit and property tests | Local logic, invariants, edge cases | Misses integration and configuration |
| Contract tests | Compatibility between independently changing services | Requires owned, versioned contracts |
| Integration tests | Real databases, queues, identity, and provider behavior | Slower and harder to isolate |
| End-to-end tests | Critical user journeys | Expensive, fragile, and poor at diagnosis |
| Performance and resilience tests | Saturation, overload, failover, and recovery | Results depend on realistic workload and environment |
| Security tests | Abuse cases, dependency risk, runtime exposure | Tool findings require triage and context |

## Build a portfolio by risk

Start with critical journeys and failure modes. Put deterministic checks early, test interfaces at ownership boundaries, and reserve broad end-to-end suites for a small number of valuable journeys. Track flake rate, time to signal, escaped defects, and whether failures identify an owner and next action.

Dynamic application security testing evaluates a running system, while static analysis evaluates source or artifacts without exercising the deployed application. Neither replaces threat modeling, authorization tests, dependency controls, or manual analysis of high-risk changes.

Canary and A/B techniques answer different questions: a canary limits deployment risk; an A/B experiment compares product outcomes. A safe experiment still needs operational abort conditions.
