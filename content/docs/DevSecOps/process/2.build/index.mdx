# Build Systems

A build transforms reviewed source into an identifiable artifact. A mature build answers four questions: what inputs were used, which trusted process ran, whether the result is reproducible enough to investigate, and which evidence follows the artifact into release.

## Build contract

- Pin toolchains and dependencies through lock files or equivalent constraints.
- Isolate builds from undeclared host state and restrict network access where practical.
- Cache by declared inputs; treat cache poisoning as a supply-chain risk.
- Generate immutable version identifiers, dependency inventory, and provenance.
- Keep credentials out of build output, logs, layers, and untrusted pull-request jobs.
- Promote one artifact across environments instead of rebuilding per environment.

## Improve performance safely

Measure queue time, checkout, dependency resolution, compilation, tests, upload, and retry separately. Parallelize independent work and use content-addressed caching, but preserve deterministic failure reporting. A faster build that intermittently returns stale or incomplete results lengthens the real feedback loop.

## Review questions

- Can the same commit produce materially different artifacts?
- Can unreviewed code access signing or production credentials?
- Which dependency or base image can change without a source change?
- Can an operator trace a production artifact to source, builder, checks, and approval?
