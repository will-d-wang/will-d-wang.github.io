# Deployment

Deployment changes a running system; release changes who can use a capability. Separating them with staged exposure or feature flags can reduce risk, but it also creates lifecycle and cleanup work.

## A safe deployment path

1. Select an immutable artifact and versioned configuration.
2. Validate policy, environment prerequisites, and database compatibility.
3. Deploy to a bounded cohort or failure domain.
4. Verify technical health and a critical user journey against predefined thresholds.
5. Continue, stop, roll back, or roll forward from observed evidence.
6. Record the artifact, configuration, identity, approval, result, and recovery action.

Use expand–migrate–contract for database changes so old and new application versions can coexist. Test rollback before relying on it; data mutations and external side effects may make roll-forward safer.

## Deployment strategies

- **Rolling:** efficient default when mixed versions are compatible.
- **Canary:** limits exposure and compares a small cohort before expansion.
- **Blue/green:** provides fast traffic switching but duplicates capacity and does not solve data compatibility.
- **Feature flag:** separates code deployment from exposure; flags need ownership and removal dates.

IaC reduces configuration drift and creates reviewable change records, but it does not eliminate human error. Module defects, incorrect requirements, unsafe plans, excessive permissions, and untested recovery can reproduce mistakes consistently.
